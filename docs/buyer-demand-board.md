# 買方客需媒合看板（相信共好大聯盟）— MVP 可行性分析與架構

給「相信共好大聯盟」旗下房仲刊登買方客戶需求（客需）、供全體同業與買家自由
瀏覽配對的看板，並提供右側廣告版位供後台販售刊登。本文件先做 MVP 可行性分析，
再展開完整資料與介面設計。

---

## 一、MVP 可行性分析

### 1. 要解決的問題

房仲手上常有「買方已委託但還沒配到適合物件」的客需，傳統做法是丟到 LINE 群組，
訊息量大、容易洗版、也無法篩選/搜尋，時間一久舊客需就找不到。核心價值：把分散
在群組裡的客需，集中變成「一張可篩選、可搜尋、隨時可查」的總表，並讓刊登者的
品牌與聯絡方式（尤其 LINE）清楚曝光，加速同業/買方直接私訊配對。

### 2. 核心使用者與情境

| 角色 | 情境 |
|---|---|
| 刊登房仲 | 手上有買方客需，想讓更多同業/賣方看到，換取「有人手上剛好有適合物件」的配對機會 |
| 瀏覽同業 | 手上有待售物件，想主動比對「有沒有人在找這種物件的買方」 |
| 買方本人（間接） | 房仲代為刊登，買方通常不會直接使用後台 |
| 聯盟管理者 | 負責審核內容品質、管理廣告版位與刊登秩序 |

### 3. MVP 範圍界定（做什麼 / 先不做什麼）

**MVP 一定要有：**
- 免登入即可刊登客需的表單（比照現有 LINE 助理後台走 ADMIN_TOKEN 保護管理端，
  但「刊登」與「瀏覽總表」對聯盟成員開放，先不做完整會員系統）
- 客需總表：可依行政區、類型、總價區間篩選/排序，含 LINE 快速聯絡按鈕
- 廣告版位：後台可上架/下架/排序，前台右側輪播顯示，記錄曝光與點擊數
- 基本防濫用：簡單防重複送出、必填驗證、後台可下架不當內容

**MVP 先不做（列為延伸方向）：**
- 會員註冊/登入、房仲身份驗證（先用「品牌名稱＋手機」當作識別，不做帳密）
- 物件端刊登與雙向自動配對演算法（MVP 是人工瀏覽配對，非系統自動媒合）
- 金流／自動請款（廣告先由後台人工登打「已收費」狀態，不做線上刷卡）
- 站內訊息／通知（聯絡方式仍是外部 LINE，不做站內聊天室）

這樣切的原因：先驗證「集中刊登 + 總表瀏覽」這個核心動作是否真的比丟群組更有效率、
房仲是否願意把客需搬進來刊登，再決定要不要投入會員系統、金流、自動媒合等重工程。

### 4. 技術路線與風險

沿用現有 `House` 專案已驗證的技術棧（Node.js + Express + 單檔 JSON 資料庫 +
無框架純 HTML/JS 後台），理由：
- 與既有 LINE 新聞助理共用同一個伺服器/部署管線，維運成本最低
- 團隊規模與資料量（客需筆數、廣告則數）在中小型範圍內，JSON 檔案已足夠，
  未來量大再比照 README 既有建議換成 SQLite/PostgreSQL
- 不需要即時雙向通訊，純粹「刊登 + 瀏覽 + 篩選」用一般 REST API 即可

主要風險與因應：
| 風險 | 因應 |
|---|---|
| 開放刊登被灌垃圾資料/廣告 | 後台可下架、必填欄位驗證、可加驗證碼（延伸） |
| 手機/LINE 等聯絡資訊外洩濫用 | 僅呈現必要聯絡方式，不索取買方本人個資，未來可加「揭露聯絡方式」按鈕統計誰查看過 |
| JSON 檔案資料庫併發寫入 | MVP 流量不高可接受，量大時依既有規劃換 DB |

## 二、資料模型

### 2.1 客需刊登（buyerRequests）

```jsonc
{
  "id": "br_xxx",
  "agentBrand": "○○房屋 信義店",      // 經紀人品牌名稱
  "agentPhone": "0912345678",         // 聯絡手機
  "agentLine": "https://line.me/ti/p/xxxxx", // LINE 個人連結或 LINE ID
  "clientCode": "A-0231",             // 客戶代號（不揭露真實姓名）
  "district": "大安區",                // 行政區
  "propertyType": "電梯大樓",           // 類型：華廈/電梯大樓/透天/店面/土地...
  "budgetMin": 1500,                   // 總價預算下限（萬元）
  "budgetMax": 2000,                   // 總價預算上限（萬元）
  "conditions": "3房2廳、屋齡15年內、近捷運",  // 條件
  "remark": "可全現金交易，配合度高",     // 備注
  "status": "published",               // published | hidden（後台下架）
  "createdAt": "2026-09-01T02:00:00Z",
  "updatedAt": "2026-09-01T02:00:00Z"
}
```

### 2.2 廣告版位（ads）

```jsonc
{
  "id": "ad_xxx",
  "title": "○○建設 - 新案預售",
  "imageUrl": "https://.../banner.jpg",
  "linkUrl": "https://...",
  "sponsor": "○○建設",
  "position": 1,                 // 顯示順序，數字越小越前面
  "startDate": "2026-09-01",
  "endDate": "2026-09-30",
  "paidStatus": "paid",          // paid | unpaid，後台人工登打收費狀態
  "status": "active",            // active | inactive
  "impressions": 0,               // 曝光次數（前台載入時 +1）
  "clicks": 0,                    // 點擊次數
  "createdAt": "2026-09-01T02:00:00Z"
}
```

## 三、頁面配置（`public/buyer-board.html`）

```
┌─────────────────────────────────────────────────────────┐
│ Header：標題 + 「＋刊登客需」按鈕（展開下方表單）             │
├─────────────────────────────┬───────────────────────────┤
│ 篩選列：行政區 / 類型 / 總價區間 / 關鍵字搜尋               │
├─────────────────────────────┤   廣告欄位（右側 sidebar）   │
│ 客需刊登表單（預設收合）        │   - 依 position 排序        │
│  品牌名稱／手機／LINE／客戶代號  │   - 顯示中且在效期內才顯示    │
│  行政區／類型／預算／條件／備注  │   - 點擊記錄 click，導向    │
├─────────────────────────────┤     linkUrl 開新分頁         │
│ 客需總表（表格）                │                            │
│  品牌 | 客戶代號 | 行政區 | 類型 │   後台廣告管理入口         │
│  | 預算 | 條件 | 備注 | LINE聯絡 │   （輸入 ADMIN_TOKEN 後     │
│  按鈕 | (後台模式)下架按鈕      │    才顯示管理表單）          │
└─────────────────────────────┴───────────────────────────┘
```

- 「LINE 聯絡」按鈕：`agentLine` 若為完整網址則直接開啟；若只是 LINE ID，組成
  `https://line.me/ti/p/~{id}` 導向，一鍵開啟 LINE 對話。
- 後台管理沿用既有 `ADMIN_TOKEN` 機制（同新聞助理後台），輸入正確 token 後才
  能看到「下架客需」「新增/編輯/刪除廣告」等操作按鈕。

## 四、API 設計

| Method | Path | 說明 | 權限 |
|---|---|---|---|
| GET | `/api/buyer-requests` | 列表，支援 `district`/`type`/`minBudget`/`maxBudget`/`keyword` query | 公開 |
| POST | `/api/buyer-requests` | 新增刊登 | 公開 |
| PATCH | `/api/buyer-requests/:id` | 編輯內容 / 下架上架 | 需 ADMIN_TOKEN |
| DELETE | `/api/buyer-requests/:id` | 刪除 | 需 ADMIN_TOKEN |
| GET | `/api/ads` | 取得目前有效廣告（前台用） | 公開 |
| GET | `/api/ads/all` | 取得全部廣告（後台管理列表用） | 需 ADMIN_TOKEN |
| POST | `/api/ads` | 新增廣告 | 需 ADMIN_TOKEN |
| PATCH | `/api/ads/:id` | 編輯廣告／上下架／收費狀態 | 需 ADMIN_TOKEN |
| DELETE | `/api/ads/:id` | 刪除廣告 | 需 ADMIN_TOKEN |
| POST | `/api/ads/:id/click` | 記錄一次點擊 | 公開 |

刊登（POST /api/buyer-requests）刻意不設 ADMIN_TOKEN 保護，因為目標使用者是
聯盟內所有房仲，要求每人先取得後台金鑰不符合 MVP 精神；下架/刪除/廣告管理則
沿用既有的管理端保護機制。

## 五、分階段規劃

1. **Phase 0（本次交付）**：客需刊登表單、總表瀏覽＋篩選、LINE 快速聯絡、
   廣告版位（後台管理＋前台顯示＋點擊/曝光統計）。
2. **Phase 1**：簡單防濫用（送出頻率限制、關鍵字黑名單自動隱藏待審）、
   客需到期自動下架（例如 30 天未更新自動標記過期）。
3. **Phase 2**：房仲帳號機制（取代目前純手機辨識）、「已配對/已成交」標記、
   配對成功回報統計，作為聯盟績效指標。
4. **Phase 3**：物件端刊登 + 系統依條件自動配對建議、廣告線上金流串接。
